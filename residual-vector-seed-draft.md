# Paired residual-seed conversion: private candidate 6

This private experiment was activated and compiled in v17. All 66 focused GPU
tests passed, including exhaustive byte-pair comparisons and graph capture.
Candidate 5 and the deployed policy remain unchanged. Historical `.draft`
copies and the original unified diff remain available for review.

## What the measured kernel spends work on

The reference is the SM120 candidate 5 profile at `M=522240, N=64, K=64`, packed
FP8 residual/input/weight, packed output, and no raw side output:
[`residual-fp8-522240x64x64-v5-20261003T014447_903827Z`](../profile/residual-fp8-522240x64x64-v5-20261003T014447_903827Z/analysis/full.txt).

[machine-readable evidence](../outputs/residual_candidate5_seed_analysis.json)

kernels in the extension.

The launch has enough CTAs to occupy the GPU; registers limit residency to four
CTAs per SM, ahead of shared memory's five-CTA limit. NCU attributes about 42.3%
of the interval between issued instructions to long-scoreboard waits. The
63% excessive-sector fraction points to scattered narrow loads as an actionable
source of wasted requests. No local/shared spills were measured. PM sampling
exists in the source report, but its aggregate samples include the surrounding
collection interval; this draft does not infer a tail imbalance from those
aggregate values.

For each thread's 16 accumulator pairs, the scalar seed path contains:

| Static SASS instructions | Count |
|---|---:|
| `LDG.E.U8` residual loads | 32 |
| `LDG.E.U16` scale loads | 32 |
| `F2FP.F16.E4M3.UNPACK_B` | 32 |
| `HADD2.F32` | 32 |
| `F2FP.F16.F32.PACK_AB` | 32 |
| `HMUL2` | 16 |

The last two conversion groups arise from decoding a byte to half, converting
that half to float, then converting it back to half. All finite E4M3 values are
exactly representable in half, so the float detour adds no precision.

## Candidate 6

Candidate 6 keeps candidate 5's `BM128/BN64/BK64`, single shared operand stage,
ordered K32 MMA sequence, partition accumulation, and output epilogue. It adds
only a compile-time `VECTOR_RESIDUAL=false` flag. Existing variants use the
unchanged scalar helper; only explicit private variant 6 enables the new path.
No policy can choose candidate 6 yet.

For each accumulator pair, the new helper:

1. Loads two adjacent residual bytes with an aligned 16-bit load when possible.
2. Maps each E4M3 NaN encoding (`0x7f`, `0xff`) to positive zero. It preserves
   every finite encoding, including negative zero (`0x80`).
3. Converts the pair directly with `__nv_cvt_fp8x2_to_halfraw2`.
4. Loads two channel scales with an aligned 32-bit load when possible.
5. Uses the same `HMUL2` result as the first MMA's half accumulator seed.

Odd-width rows, final unpaired channels, and storage-offset views take safe
scalar loads. A pair never crosses a row or scale-array boundary. The new
helper introduces no allocations, barriers, scratch storage, or per-launch
device queries. Output publication and raw-output ownership remain unchanged.

This removes conversion and memory-request overhead, as the compiled SASS and
NCU comparison below confirm. It does not reduce the unique residual/scale bytes
or the matrix work. Alignment tests, scalar fallback branches and NaN masking
also cost instructions, so the result remains shape-dependent.

## Tests and activation boundary

The implementation, probe, tests and benchmark now have active files with the
same names without `.draft`. The links below preserve the original proposal;
the unified diff was applied with the default flag left false:

- [Paired helper](../csrc/kernel_impl/residual_seed_vector.cuh.draft)

  generated by [draft_residual_vector_seed.py](../tools/draft_residual_vector_seed.py)
- [Seed-only CUDA probe](../csrc/kernel_launcher/residual_seed_probe.cu.draft)
  and [private registration](../csrc/torch_api/residual_seed_probe.cpp.draft)
- [66 GPU test cases](../tests/test_residual_vector_seed.py.draft)
- [Same-I/O candidate 5 versus 6 benchmark](../tests/benchmark_residual_vector_seed.py.draft)

The GPU tests compare every ordered pair of E4 bytes under four finite scale
patterns, both aligned and offset views, against the old scalar seed helper and
an independent NumPy bit-level oracle. The seed-only probe is necessary because
MMA can change a signed zero even when seed conversion itself is correct.
Additional cases cover odd widths, empty matrices, partition boundaries, all
published/raw output combinations, immutable inputs, and graph replay after
mutating NaN-containing residuals and offset scales.

The existing standalone `inference_residual_seed` preserves E4 NaNs, while the
existing fused GEMM helper maps them to positive zero. These bytes cannot come
from the model's finite publication operator, but arbitrary byte inputs can
expose the difference. This draft preserves the fused helper's contract. Tests
sanitize only the independent composed oracle's input before comparing it;
they do not hide a candidate 5/6 mismatch or alter the live standalone operator.

The [CPU proof](../tools/probe_residual_vector_seed.py) passed all 65,536 ordered
byte masks and 2,180,100 address/scale combinations. The
[result](../outputs/residual_vector_seed_cpu.json) pins draft source hashes.
The 66 focused CUDA conversion/capture tests passed in the
[420-test v17 run](../outputs/v17-focused-tests.xml). These same 66 tests also
passed inside the [368-test sanitizer run](../outputs/v17-new-kernels-memcheck.log),
which reported zero memory errors. These results validate the tested SM120
contracts; they do not constitute testing on every supported architecture.
The benchmark retains distinct outputs for repeated invocations in a
single graph, caps captured output at 256 MiB, and compares variant 6 directly
against resident variant 5. It never exports a policy.

The [v17 measurements](../outputs/residual_vector_v17.json) compare candidate 6
directly with candidate 5. For M=18,432, N=K=64, the four output contracts improve
by 1.050x to 1.069x. At M=522,240, improvements range from a slight regression
(0.984x) to 1.020x. The odd-width N=63 case regresses to 0.943x–0.975x. These
results support selective measurement rather than replacing candidate 5 for
all shapes. All 24 measured contracts passed bit-exact output and immutable-input
checks. Candidate 6 remains private and is absent from the deployment policy.

## What the candidate 6 profile actually changed

The [candidate 6 report](../profile/residual-fp8-522240x64x64-v6-20261003T025233_161387Z/analysis/full.txt)
uses the same `522240 x 64 x 64` packed-only scope as candidate 5, with NCU's
`cache-control=all`. It pins the v17 extension SHA256 beginning `0790676a673a`.
The [reproducible comparison](../outputs/residual_vector_profile_comparison.json)
and [extracted candidate 6 SASS](../outputs/residual_candidate6_profile.sass.txt)
are generated by [analyze_residual_vector_profile.py](../tools/analyze_residual_vector_profile.py).

| Measurement | Candidate 5 | Candidate 6 |
|---|---:|---:|
| Cold profiled duration | 57.888 us | 56.544 us |
| DRAM throughput | 67.61% | 69.39% |
| L2 throughput | 29.35% | 29.56% |
| Tensor-pipe activity | 8.96% | 9.09% |
| Issued instructions | 46,348,800 | 45,010,560 |
| Global sectors / excessive sectors | 12,794,880 / 8,094,720 | 8,094,720 / 3,916,800 |
| Shared wavefronts / excessive wavefronts | 4,341,120 / 1,468,800 | 4,341,120 / 1,468,800 |
| Registers/thread / static shared memory | 64 / 18,432 bytes | 64 / 18,432 bytes |
| Achieved occupancy | 62.84% | 63.43% |

The intended conversion simplification survived compilation: the exact selected
symbol has 16 E4-pair-to-half conversions instead of 32, and the 32 `HADD2.F32`
plus 32 `F2FP.F16.F32.PACK_AB` instructions disappear. There are 16 aligned
32-bit scale loads and paired 16-bit residual loads on the fast path. The same
16 `HMUL2` seed multiplies and 16 static QMMA instructions remain.

The whole symbol grows from 1,184 to 1,392 static instructions because it also
contains alignment tests and scalar fallback branches. Counting all static
`LDG` instructions would therefore misrepresent the aligned executed path.
The measured workload issues 2.89% fewer instructions and 36.73% fewer global
sectors, while shared traffic and register-limited residency are unchanged.
This explains why eliminating many narrow requests produces only a modest
latency improvement in this large case.

The candidate still spends about 42.2% of its instruction-issue interval waiting
on long-scoreboard dependencies; NCU reports only 8.9 useful bytes per 32-byte
global-load sector. These observations support examining further coalescing or
latency hiding, but do not prove that an additional shared staging pass will
help. The separate cold-cache runs cannot replace the resident graph benchmark
or establish small timing differences statistically. The best measured
throughput is **69.39%**, so the requested **85% gate is not met**.

## A possible later staging experiment

If profiling shows that narrow global loads still dominate after paired
conversion, a separate candidate could fill an 8,192-byte packed residual tile
inside the existing 18,432-byte shared workspace, synchronize, read the seed
pairs into registers, synchronize again, then reuse that storage for A/W
operand staging. This would add no shared allocation but would add two CTA
barriers and shared traffic before matrix loads. It could improve global
coalescing, or it could delay the MMA pipeline enough to lose. It is a hypothesis,
not part of candidate 6. Candidate 6's remaining narrow-load and long-scoreboard
cost now supplies a measured motivation, but the extra barriers still need an
independent timing experiment.
