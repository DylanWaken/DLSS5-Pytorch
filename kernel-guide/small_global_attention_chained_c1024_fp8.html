01. The whole problem and the target precision contract

Target model operation. Small31's C1024 bottleneck contains eight global-attention blocks (scheduler operation-role labels 31–38, distinct from archive raw IDs 0–30), each with 32 heads of 32 channels. This FP8 kernel connects their QKV producer to the attention-output projection: each query reads every key and combines the associated V features. The worked 4K case has 2,160 model positions, including spatial padding; the key stream extends to 2,176 positions to fill its final tile.

Derive the token count from the model geometry. A 3840×2160 frame first uses a 3840×2176 frontend field. Each encoder level applies align_up(ceil(previous/2), 4) independently to width and height. Levels 0…5 are 1920×1088 → 960×544 → 480×272 → 240×136 → 120×68 → 60×36. The last height is ceil(68/2)=34, then rounded to 36, so the bottleneck has T=60×36=2,160 model positions. This includes level-5 spatial padding. The separate 32-token host allocation rounds T to 2,176; the attention kernel's 256-query CTA grid covers 2,304 query slots. These are three different extents.

D[q] = Σk E(q,k),   u[q,c] = Σk E4M3(E(q,k)) · V[k,c],   y[q,c] = publish( u[q,c] / max(D[q], ε) ).

Hardware target. Map this operation to an SM120-class GPU with 128-thread CTAs, mma.sync tensor instructions and explicitly addressed shared storage. The source uses __maxnreg__(208); the Half entry admits SM80+ and the E4M3 entry SM89+, while the measured binary is SM120. Derive the tile and live-state budget first, then compare it with the compiler and experiment results in section 6.

Q and K are normalized per 32-channel head upstream. Q is then multiplied by sqrt(32) and a learned per-head Half scale; K is not scaled by that head factor. V is not normalized and is not unit-bounded; the QKV producer transposes its fragments before publication. This entry does not change Q, K, V, the ABI, the token addresses or the padded-key obligation. It changes only the finite-precision accumulation contract of u and D.

The QK accumulator is Half in both entries. The surrogate is a fixed positive map, not a row-max softmax: no max subtraction, no exp, no normalization inside E. Each Half lane of a score pair gets its own affine transform and clamp; the whole-word shift and offset then act on the packed pair, so the native carry between lanes is part of the encoding. The exact positive interval is [0.0040283203125, 1.640625]; a zero score encodes to E0 = 0.083984375.

Why widen the accumulator? E is positive, so D is positive and the ideal FP16-path result before arithmetic rounding is a convex mixture of V rows with weights E/D. The final value can be modest while a prefix is huge: uj = Σk≤j E·V is unnormalized, and every prefix must stay finite. Later opposite-sign terms cannot repair an earlier Inf or NaN. Half has largest finite magnitude 65,504; overflow can produce infinity. FP8 satfinite publication is a separate conversion rule. FP32 has a far larger exponent range. This is a forward-range decision, not a tuning history.

FP8 is not an exact convex hull. The denominator sums the original Half E, but the numerator's P operand is E4M3(E). If E4(E)=E+δ, then u = ΣE·V + Σδ·V while D = ΣE. The output is a convex mixture plus a perturbation bounded by the E4M3 allowance: about half an E4M3 ulp per normal term (≈6.25% relative), with an absolute allowance below the normal range. Do not use an FP16 convex-hull oracle for FP8 without that allowance. Padding uses E(0)=0.083984375; at T=2,160 the 16 padded keys add 16 × 0.083984375 = 1.34375 to each denominator, removed in FP32, and zero to the numerator because their V is zero.

02. One CTA: one head, 256 queries, a 64-key stream

Choose one head per CTA. The launch grid is (blockIdx.x = 32 heads, blockIdx.y = ceil(T/256) = 9 query blocks) with block = (32 lanes, 4 warps). A CTA owns 256 queries of one head, divided into four warps of 64 queries; each warp owns four M16 query tiles. For block 0, warp 0, query tile 1, the 16-token group is 0·16 + 0·4 + 1 = 1, covering global queries 16…31; query 17 is local row 1.

Keys stream through a two-slot ring. Each stage holds 64 keys × 32 channels × 1 byte = 2,048 bytes for K and the same for V. The four slots K0, K1, V0, V1 occupy 4 × 2,048 = 8,192 bytes, followed by two 8-byte barriers, so the static shared declaration is 8,208 bytes per CTA. There is no XOR shared-memory swizzle in this kernel: the producer writes a prepacked 16-byte panel per lane and the consumer reads the same panel at a 512-byte stride.

Q is loaded once with __ldca into registers. K and V are bulk-copied into s_Storage and read back as uint4 vectors. These are three storage layers: a hardware-managed global route for Q, a bulk global-to-shared copy for K/V, and explicit shared addressing for the ring. The source does not promise that the bulk copy allocates an L1 line.

2.1 The exact K and V publication maps

K uses Q's 16-token-group × 32-channel-head layout: group·16384·E + head·512·E + keyChunk·512. FP16 has a 32,768-byte group and a 1,024-byte head plane; FP8 has 16,384 and 512. V deliberately does not use that map. Its transposed fragments are addressed by group·32768 + head·1024 + (CopySlot & 1)·512, independent of element size. The 32,768-byte V group holds 16 tokens in FP16 and 32 in FP8, so its head plane is 1,024 bytes in both. Treating V as dense token×channel, or as byte-identical to Q, gives wrong offsets.

Both kernels have 34 key tiles, covering keys 0…2,175. There are no fictional keys beyond 2,175. In the last tile, keys 2,160…2,175 are the 16 pad keys. FP16 zero-fills the last K/V group in shared memory because group 135 is not below g_Groups16=135. FP8 has g_Groups16=136, so group 135 is a valid copy of the upstream QKV output. That output is zero there because the upstream repack explicitly writes +0 for tokens beyond the real count (r_CopiedWord = 0 guarded by g_TokenIndex < g_TokenCount), and QKV group 135 consumes exactly that tail. The downstream arithmetic is identical: encoded zero score gives E0 for those keys, and V is zero.

The last query block (blockIdx.y = 8) owns global queries 2,048…2,159: 112 real queries, not 256. 03. Warp and lane ownership: 64 FP32 numerators, two FP32 denominators

One warp owns 64 queries × 32 channels = 2,048 values, or 64 per lane. The source stores them as float r_Output[4][4][4]: four M16 query tiles × four N8 output groups × four native D registers. D0/D1 are the two lane-owned columns of row Lane/4; D2/D3 are the same columns of row Lane/4+8. The row denominator is float r_Denominator[2] (low 32, high 32 queries). That is 66 persistent FP32 words per lane.

QK uses MmaWindowFragment<bFp8> and accumulates Half C/D. PV uses MmaWindowFragmentF32<bFp8>: FP16 selects mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32; FP8 selects mma.sync.aligned.m16n8k32.row.col.f32.e4m3.e4m3.f32. Operand and D layouts match, so the P/V lane map is unchanged; only the accumulation format of PV changes.

3.1 The worked query: q17, head 7, channel 9

Query 17 is global token 17. CTA (7,0), warp 0, query tile 1, local row 1. With g = Lane/4 = 1, q = Lane%4 = 0, lane 4 owns the row. Channel 9 is N8 group 1, column pair 0, so the value is r_Output[1][1][1]; channel 8 is [1][1][0]. The query's 32 channels are spread over lanes 4…7.

Final normalization computes QueryRow = 1·16 + 4/4 + 0 = 17, selects the low FP32 denominator because r_QueryTile < 2, and calls ShuffleIdx(..., 17, 31, 0xffffffff). Output owner: lane 4. Denominator owner: lane 17. The PV fragment is distributed by output column; the row reduction is transposed to one query per lane.

3.2 The FP32 denominator gather and lane 17

The row reduction is the only place where the warp's query halves are recombined. Each lane has four local float2 sums per query half; each local sum holds 16 keys. The q17 partial is r_LocalProbabilitySums[2] in each of lanes 4,5,6,7; its float2 components hold even/odd key columns of the same query. The receiving lane 17 uses sourceLane = ((17 & 7) << 2) + (17 >> 3) = 6. The gathers read source lanes 6,7,4,5; the second permutation with Lane >> 3 = 2 swaps words 0↔2 and 1↔3, so the addition order is 4,5,6,7. Four sources × 16 keys = 64 keys = one key tile. The even/odd key-component combine is one FP32 TotalFloat2, and r_Denominator[0] += carries it across tiles.

04. Resource budget before implementation

Start with the threads and the intentional live state, not with a profiler number. A CTA has 128 threads (32 lanes × 4 warps) and owns 256 queries. The persistent per-lane state is 66 FP32 words; the per-CTA logical total is 128 × 66 × 4 = 33,792 bytes. The legacy Half body's comparable logical state was 16,896 bytes, so the persistent delta is 16,896 bytes. That delta is a live-value calculation, not a compiler register-file delta, not local-memory traffic, and not occupancy.

Instruction work is also source-derived. Per warp per key tile, QK issues 4 query tiles × 8 N8 groups × 1 reduction chunks = 32 MMA calls. PV issues 4 query tiles × 4 N8 outputs × 2 probability chunks = 32. That is 64 PTX mma.sync calls per warp per key tile, or 256 per CTA per tile. Across 34 key tiles, one CTA's four warps issue 8,704 PTX calls in this source program. These are PTX program counts, not measured SASS instruction totals; NCU SourceCounters is the only evidence that can replace them. Tail query tiles still execute the loops and are suppressed only at the store; the count above already includes that work.

Before measuring anything, require four correctness gates: (1) a scalar FP32 oracle that validates connectivity and token/channel ownership; (2) a one-key-tile version that checks the Half QK/E path and the FP32 denominator tree against the same terms in the same order; (3) a streamed 34-tile version that checks the cross-tile FP32 carry and both ring wraps; (4) a tail fixture at 16/32/64/128/256 tokens that checks zero fill, the explicit FP8 zero tail, the pad correction and the completion counters. The compiled-resource check follows those gates; it does not substitute for them.

05. Execution: two-stage ring, persistent state and construction milestones

The schedule has one non-negotiable dependency: the persistent u and D must survive every key tile, while K, V, score and E tiles are consumed and replaced. The ring exists to keep the key axis moving without making the score tile persistent. It is not a throughput claim and it does not create a fixed warp/CTA timeline.

5.1 Construction milestones

Build the entry in this order; each milestone has a falsifier and none of them requires a performance measurement.

  1. Scalar oracle. Compute D and u in FP32 from decoded Q/K/V for tagged queries including q17/head7/c9. Falsifier: a transposed V, wrong head plane or wrong q pair. This proves connectivity, not bitwise packed-E equality.
  2. One key tile. Check the Half QK/E path and the FP32 denominator tree against the same terms. Falsifier: a Half tile total, an E4 denominator term, or a lost low/high lane.
  3. Stream all tiles. Enable 34 tiles and both ring wraps; check the FP32 carry order and that no tile is consumed twice. Falsifier: parity-only waits or an overwrite of unread K/V.
  4. Numerical budget. Add the pad correction and epsilon clamp; the 16 padded keys must add 1.34375 to each denominator and zero to the numerator. Falsifier: a Half-rounded correction.
  5. Ring pipeline. Replace synchronous copies with the two-ahead ring and compare the full output. Falsifier: a stale slot, missing barrier arrival, or a final-tile wait.
  6. Publish and count. Add the FP32 multiply, one Half publication, optional E4 conversion, tail clear and release counter. Falsifier: an unrounded store or an early counter.
  7. Validation. Re-run the oracle, tail fixture, both ring wraps and the counter dependency test before requesting a compiled-resource/NCU handoff.

6.10.3 K/V shared vectors, banks and the local-memory path

SASS shows LDS.128 for the K and V shared loads. A 128-bit per-lane load over 32 lanes is a 512 B warp request, which legitimately needs four 128 B shared wavefronts. The measured shared-load wavefronts per instruction are 4.0002 (1,253,431 wavefronts / 313,344 instructions) for this entry; the derived excessive-wavefront count is 0 and the ideal equals the observed wavefront count. The separate hardware counters report 63 shared-load bank conflicts. The source-derived ideal and the hardware bank-conflict counter have different scopes: zero derived excess does not erase the measured conflicts or establish their runtime cost. The source has no XOR shared-memory swizzle; the producer writes a prepacked 16-byte panel per lane and the consumer reads it at a 512-byte stride. Do not infer conflicts merely from repeated bank numbers in a whole-warp 512 B request.

FP8 removes the local-memory path. The full report records zero local loads, zero local stores, zero local sectors and zero spill instructions, and the source run has no direct LDL/STL PCs. There is therefore no FP8 spill runtime share to attribute; this does not imply that FP16 spills dominate its own time. The sampled categories are wait 1,055 (21.29%), barrier 747 (15.07%), math-pipe throttle 356 (7.18%) and long scoreboard 325 (6.56%). These samples identify candidate dependencies; they do not prove that spills dominate total time, and cap 224 is an untested follow-up, not an implemented optimization.

215				}

218				// into one full query sum per lane. It permutes and shuffles whole
219				// FP32 component pairs, so the recovered lane mapping is unchanged.

221				PermuteGlobalAttentionQuadFloat2(r_LocalProbabilitySums, TileCoordinates.Lane & 3);
222				#pragma unroll

228													  r_GatheredProbabilitySums[1]);

230				r_Sum = AddFloat2Componentwise(r_Sum, r_GatheredProbabilitySums[3]);

232				// halves; keep that final logical step in FP32 as well.

234			}

236			// P operand below is their E4M3 conversion; the whole row reduction
237			// and its running cross-key-tile carry are now FP32.

253			#pragma unroll

263								   r_UpperValueFragment[2] = {r_ValueVector.z, r_ValueVector.w};

265											   r_Output[r_QueryTile][r_ColumnTile * 2]);

281	// denominator without the intermediate packed-Half round trip.
282	uint32_t r_InverseDenominatorLow, r_InverseDenominatorHigh;
283	{

285		if (PaddingKeys > 0)

288			// The correction is the exact product of that Half value and the
289			// padded-key count, subtracted from both FP32 row totals.
290			const uint32_t r_AffineZero =
291				HalfFma(0, CONST_GLOBAL_EXP_SLOPE_HALF2, CONST_GLOBAL_EXP_INTERCEPT_HALF2);
292			const uint32_t r_ClampedZero =
293				HalfMin(HalfMax(r_AffineZero, CONST_GLOBAL_EXP_LOWER_HALF2), CONST_GLOBAL_EXP_UPPER_HALF2);
294			const uint16_t r_ZeroScore =
295				uint16_t((uint16_t(r_ClampedZero) << CONST_GLOBAL_EXP_ENCODING_SHIFT) +
296						 CONST_GLOBAL_EXP_SCALAR_OFFSET);

298				FloatMulFtzBits(HalfToFloatBits(r_ZeroScore), UintToFloatRnBits(PaddingKeys));
299			r_Denominator[0] -= __uint_as_float(r_CorrectionBits);
300			r_Denominator[1] -= __uint_as_float(r_CorrectionBits);
301		}

304		// clamp value and the NaN choice stay those of the recovered kernel.
305		const float r_Epsilon =
306			__uint_as_float(HalfToFloatBits(uint16_t(CONST_NORMALIZATION_EPSILON_HALF2)));
307		r_InverseDenominatorLow =
308			__float_as_uint(ApproxRcp(ClampDenominatorFloat(r_Denominator[0], r_Epsilon)));
309		r_InverseDenominatorHigh =
310			__float_as_uint(ApproxRcp(ClampDenominatorFloat(r_Denominator[1], r_Epsilon)));
311	}

314	// Half, then publish through the unchanged Half-to-E4M3 contract.
315	#pragma unroll

317	{
318		FWindowAccumulatorTile<32> r_NormalizedOutput;
319		#pragma unroll

321		{
322			const int QueryRow = r_QueryTile * 16 + TileCoordinates.Lane / 4 + r_Half * 8;
323			const uint32_t r_LocalInverse =
324				r_QueryTile < 2 ? r_InverseDenominatorLow : r_InverseDenominatorHigh;
325			const float r_QueryNormalization = __uint_as_float(
326				ShuffleIdx(r_LocalInverse, QueryRow % 32, 31, 0xffffffffu));
327			#pragma unroll
328			for (int r_ColumnTile = 0; r_ColumnTile < 4; ++r_ColumnTile)
329				r_NormalizedOutput.r_Pair[r_ColumnTile][r_Half] = PackFloatColumnsHalf2(
330					r_Output[r_QueryTile][r_ColumnTile][2 * r_Half] * r_QueryNormalization,
331					r_Output[r_QueryTile][r_ColumnTile][2 * r_Half + 1] * r_QueryNormalization);
332		}

335		if (g_Group < TileCoordinates.g_Groups16)
336			#pragma unroll
337			for (int r_Chunk = 0; r_Chunk < Profile::QueryChunks; ++r_Chunk)
338			{
339				const auto r_OutputFragment = PublishWindowChunk<bFp8>(r_NormalizedOutput, r_Chunk);
340				StoreNoAllocate(Parameters.g_Output + uint64_t(g_Group) * 16384 * Profile::ElementBytes +
341									TileCoordinates.g_Head * 512 * Profile::ElementBytes + r_Chunk * 512 +
342									TileCoordinates.Lane * 16,
343								make_uint4(r_OutputFragment.r_Word[0], r_OutputFragment.r_Word[1],
344										   r_OutputFragment.r_Word[2], r_OutputFragment.r_Word[3]));
345			}
346	}

349	// rows after all fragment stores, then release the completion counters.
350	if (g_PaddedTokens != g_Tokens)
351	{
352		__syncthreads();
353		#pragma unroll
354		for (int r_QueryTile = 0; r_QueryTile < 4; ++r_QueryTile)
355			#pragma unroll
356			for (int r_Half = 0; r_Half < 2; ++r_Half)
357			{
358				const int g_Group =
359					TileCoordinates.g_QueryBlock256 * 16 + TileCoordinates.Warp * 4 + r_QueryTile;
360				const int g_Row = g_Group * 16 + TileCoordinates.Lane / 4 + r_Half * 8;
361				if (g_Row >= g_Tokens && g_Row < g_PaddedTokens)
362					#pragma unroll
363					for (int r_Chunk = 0; r_Chunk < Profile::QueryChunks; ++r_Chunk)
364						#pragma unroll
365						for (int r_ColumnTile = 0; r_ColumnTile < 2; ++r_ColumnTile)
366							*reinterpret_cast<uint32_t*>(
367								Parameters.g_Output + uint64_t(g_Group) * 16384 * Profile::ElementBytes +
368								TileCoordinates.g_Head * 512 * Profile::ElementBytes + r_Chunk * 512 +
369								TileCoordinates.Lane * 16 + (r_ColumnTile * 2 + r_Half) * 4) = 0;
370			}
371	}
372
373	__syncthreads();
374	if (Parameters.g_CompletionCounters && TileCoordinates.Lane == 0 && TileCoordinates.Warp == 0)
375		#pragma unroll
376		for (int g_LocalGroup = 0; g_LocalGroup < 2; ++g_LocalGroup)
377		{
378			const int g_Group = TileCoordinates.g_QueryBlock256 * 2 + g_LocalGroup;
379			if (g_Group < TileCoordinates.g_QueryBlocks128)
380				CounterStoreRelease(
381					Parameters.g_CompletionCounters + (g_Group * 32 + TileCoordinates.g_Head) * 4, 0);
382		}
383#else
384	// Keep the exported entry on older targets, but never silently skip FP8 work.
385	__trap();
386#endif
