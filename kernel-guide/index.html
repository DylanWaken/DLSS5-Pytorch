Design one kernel from its model contract

DLSS-NR is an encoder–decoder with local window attention, a global-attention bottleneck, and residual connections. Choose the model operation below. Every precision-specific lesson follows a forward design process in six sections: whole problem → one CTA → one warp/thread → resource budget → execution schedule → one token through source. Start with a correct baseline, identify its cost, derive candidate tiles and ownership, and budget their live state before implementing the schedule. Specialized diagrams make those choices concrete. The final section builds the candidate in milestones and tests its predictions against recorded SM120 evidence.

You do not need to read a family chapter first. Prerequisites are repeated inside each lesson so that the entire reasoning fits into one linear reading session. Template specializations get separate pages because width, precision and boundary mode change the contract even when they share a CUDA body.

New as of 2026-10-29: the DLSS 310.9.16 / Small31 forward-design chapter documents the separately trained 31-role model, the raw-id → operation-role mapping, the changed window phases and the strict provenance boundary. The 81 legacy kernel lessons below remain the historical 310.8/71-block implementation evidence; the two additive Small31 attention lessons use the new committed source and the explicit Small31 FP32-accumulation contract.

How to use a lesson

The six-section standard is shared by all 83 kernel lessons. The 81 original entries have full and source-counter NCU evidence, with downloadable raw reports, exact metric names, source-correlated SASS, and fixture details. The two additive Small31 attention lessons also record committed source, compiled resources, numerical-reference receipts and four current full/source NCU reports for an isolated replay of one attention call; no legacy report is reused.

Read in order and make each decision before moving on. Implement the scalar oracle, compare subdivisions, check one worked address by hand, and add each mechanism while preserving the numerical boundaries. Each change needs a correctness test and a falsifiable performance hypothesis; proposed alternatives have no implied benchmark result. Source excerpts sit beside the relevant derivation; the complete source and launch record are at the end. Diagrams distinguish global allocations, hardware-managed caches, explicitly indexed shared memory, register fragments and compute. Wide figures scroll horizontally rather than shrinking their labels.

The design progression follows the style of Anatomy of a CUDA GEMM: a limitation of the simpler implementation motivates the next mechanism. The MMA tutorial at spatters.ca also informs the lane-level teaching style. Read the experiment ledger to distinguish reconstructed design reasoning, executable arithmetic checks and actual profiler results. The per-kernel tiling atlases use the visual progression of NVIDIA’s CUTLASS hierarchy: logical matrices → CTA tiles → warp tiles → instruction fragments. Their dimensions, storage paths and token traces come from this repository’s individual kernels. Each atlas is also available as a full-size SVG download.

Source equations establish token addresses; aggregate counters do not trace a semantic token or prove a speedup. See what each kind of evidence supports.
