The model piece: the prepared-feature encoder–decoder trunk

The prepared plan implements numbered records 1–69: five encoder levels, eight C1024 global blocks, the transition at record 39, and the returning decoder levels. The complete architecture has records 0–70, but the prepared-feature benchmark starts after input preprocessing and stops before output postprocessing. The frontend chapter documents those separate entry points; the architecture guide shows the full model.

One numbered record is not necessarily one launch. A fused C32 block fits one kernel. An ordinary C512 block spans four. A C1024 block needs FFN expansion, contraction, QKV, attention and projection, with counter clearing and repacking at selected boundaries. Both current prepared plans assert 185 logical calls and 37 distinct entries (36 compute/repack plus counter clear). A capacity fallback can turn one dependent logical call into several physical launches.

1. Prepare storage before capture

Python hands the C++ plan a contiguous raw-byte GPU input plus precision-specific packed records. C++ checks the selected CUDA device, exact physical extents, 16-byte alignment and disjoint input/weight ranges. It allocates workspaces, puts 256-byte guard spans around each, and builds typed parameter blocks and buffer bindings. The plan keeps tensor ownership so addresses remain valid during execution. Creating this state happens outside CUDA Graph capture; replay can then use already-stable addresses.

The uint8 host tensor type is a storage container. It does not imply all contents are 8-bit arithmetic. FP16 activations, Half scratch, packed FP8 weights and int32 counters all live in byte-addressed allocations with distinct ABI meanings. Using an arbitrary contiguous PyTorch tensor without packing cannot satisfy the layout contract.

2. Distinguish four kinds of extent

ExtentPurpose4K example
Valid imageThe caller's requested field3840×2160
Network spatial fieldGeometry's padded levels, already part of the model's tokensFull 3840×2176; bottleneck 60×36
Physical token allocationC++ token buffers round T to a multiple of 32T=2160 → 2176 rows
Attention traversalKey loop processes 64-token tiles; missing keys are zero-filledT=2160 → 2176 visited slots

The last two agree at 4K but need not agree for other shapes. A tensor buffer allocated to a multiple of 32 does not authorize unconditional loads up to a multiple of 64. Kernels predicate their tail loads. Likewise a finite-value check should cover logical values, not assume every unused allocation byte has been initialized. The final attention denominator removes only extra traversal slots; it does not delete the spatial padding already included in T.

3. Follow a dependent split through its publication

A large contraction can partition its reduction dimension over Z. Each split computes a partial result in Half, with an explicitly ordered update to scratch. A later split must not consume scratch before the earlier producer has published it. The resident path uses global counters with the initial sentinel −1, release stores and polling reads. A CTA barrier coordinates participating threads after polling. Read the particular kernel for the expected counter value and final publication: the protocols differ, and attention's “ready” counter is not automatically a QKV split number.

The presence of AcquireSplitPublication() in the shared header does not mean every kernel calls it. For example, the decoder and some bottleneck bodies at this snapshot poll relaxed counters without that helper. These pages describe the source protocol; they do not claim a new formal memory-order proof or fresh hardware qualification.

A release store expresses publication order; a consumer must separately establish the required visibility. Cache selection alone is not an acquire operation. For ordered launches, completion and ordering on the same CUDA stream establish an inter-kernel boundary before the next split reads scratch. This is a different mechanism from spinning inside a single grid.

4. Avoid scheduling-dependent progress

Ordinary CUDA scheduling does not promise that a predecessor block runs before a block that spins on it. If waiters occupy all SM capacity while their producers have not been scheduled, a dependent full grid can fail to progress. The policy therefore compares the complete logical grid, not only one XY plane, against the number of simultaneously active blocks reported for the loaded function. With P=grid.x×grid.y, S=grid.z and capacity C=active_blocks_per_SM×SM_count, one grid is selected only when P ≤ floor(C/S). This division form avoids multiplication overflow.

Worked example: P=96 blocks per XY plane, S=4 splits and capacity C=264 gives 96 > 264/4 = 66, so the runtime issues four ordered Z=1 launches. Each 96-block plane can run in as many waves as needed. With P=48, the entire 192-block grid fits that capacity; the resident route remains available. These numbers illustrate the policy; they are not measured device resources.

5. Choose instructions and resources for the loaded device

The host admits FP16 at SM80+ and FP8 at SM89+. It checks both the loaded binary and its virtual target: compiling a body to a trapping FP8 fallback and later JITing it for a newer GPU does not create a valid FP8 implementation. Block dimensions, static shared bytes and actual occupancy also gate admission. The README's physical measurements are on RTX PRO 6000 Blackwell, SM120; compilation for Ampere/Ada and execution of lower-target code on SM120 are different evidence from running on actual SM80/89 hardware.

6. Connect each optimization to the work it saves

Source designIntended reductionWhat can offset the gainEvidence to collect
Fuse a local FFN, QKV and attentionIntermediate global writes/reads and launchesLonger register lifetimes; spills; fewer active blocksCompiled resources, local traffic, full-trunk timing

The repository's historical lessons report cases where reducing source complexity did not reduce instructions, where extra issued work was NOPs rather than additional tensor operations, and where an assembler backend changed scheduling. Those are reasons to measure the compiled workload, not promises that applying the same edit elsewhere will be faster. The tutorials explain mechanisms found in current source. They do not claim newly measured speedups.

7. Reproduce the relevant evidence

First preserve the input shape, device, precision, source revision, toolkit/assembler, packed-record identity and timing scope. Check numerical outputs and intermediate boundaries at the intended precisions. For layout edits, validate reads/writes and boundary padding; for publication edits, preserve rounding and operand order; for scheduling edits, exercise both resident and ordered paths. Only then compare paired timings with both execution orders and matching warmup/capture rules.
