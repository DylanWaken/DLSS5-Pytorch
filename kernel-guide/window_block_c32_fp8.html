01. The whole problem

Target entry: window_block_c32_fp8. This entry implements the ordinary C32 block used in records 0–4 and 66–70. Its logical input and output are both [H,W,32]. Attention relates the 64 positions in each configured 8 × 8 neighborhood. Frontend and transition records wrap this same operation with additional work. The FFN is a dense 32 → 128 → 32 map. The attention has 1 head, each with 32 channels. There is no pre-FFN LayerNorm and no sparse routing decision. Every FFN works independently at each token; the attention is where 64 positions exchange information. The architecture document is useful context, but all mechanics needed for this entry are developed below.

Write the ordinary block as Zraw=FFN(X)+sffn⊙R; Z=Publish(Zraw); Q,K,V=project(Z); A=Publish(normalize_keys(E(QKᵀ+bias))V); Yraw=project(A)+sattn⊙Zraw. This entry publishes working operands as E4M3, while the matrix accumulators, residual products, activation and reductions use packed Half arithmetic. “Raw” identifies a value before the next publication, not an FP32 promise. The model equation alone leaves reduction order and physical placement unspecified; those are the kernel-design problem.

A correctness oracle for the complete operator

Start with the following nested-loop interpretation. A token index denotes a spatial position, a channel index selects its feature, and a head index selects one 32-channel attention space. The oracle is deliberately expensive: it can materialize every hidden tensor and the 64 × 64 score matrix. It establishes which values may communicate and where publication belongs. To validate the final bit pattern, replace its abstract dot products and sums with the exact Half instruction/reduction order introduced below; a generic FP32 PyTorch implementation is only a mathematical and shape check.

A fully staged implementation would write the hidden FFN tensor, branch concatenation, QKV, scores, probabilities and attended values to global memory, then read them back in separate launches. For one head, a score tensor alone is 4096 Half values, or 8192 bytes; a separate write and read would transfer 16384 logical bytes before considering cache effects. The implementation removes these particular intermediate transfers by choosing an ownership map that keeps their producers and consumers together. The tradeoff is longer register lifetimes, and for multiple warps, explicit shared-memory synchronization.

Find the first avoidable cost

The simplest staged baseline writes each FFN hidden activation, then QKV, scores, probabilities and attended values. Across 1 heads the score tensor alone occupies 8,192 Half bytes per window. These temporaries are candidates for fusion because no later window reads them; the final [H,W,32] output remains externally observable.

The following design is a reconstruction from the model and current source. The staged baseline and alternative partitions are teaching candidates, not claims about the author’s historical experiments or measured faster/slower variants. Byte counts are logical traffic excluding weights, cache reuse and transaction overhead.

02. One CTA: its concrete subproblem

Start by assigning one output token to a thread. That is correct, but its query must read all 64 keys and values. Grouping 16 query rows in a CTA improves reuse, yet four such CTAs still need the same K/V neighborhood. One head’s K plus V is 2×64×32×1=4,096 working bytes; four independently loaded query groups request 16,384 logical bytes instead of 4,096, before cache effects. A CTA per head avoids that duplication, but the final 32→32 projection must combine all heads and would need another exchange or launch. These dependencies motivate trying one CTA per complete window.

The selected subproblem therefore includes 64 FFNs, 1 Q/K/V projections, every 64×64 head interaction and the final cross-head projection. Its scope is an algebraic consequence of local attention; the choice to fit it into one CTA is an implementation decision. The view adapter, when present, changes where this domain is loaded or stored rather than which tokens attend each other.

Make that choice concrete on a 16×16 field: a 2×2 CTA grid covers four unshifted windows; CTA(1,0) starts at (8,0). With a phase offset, use (8·blockIdx.x+OriginX,8·blockIdx.y+OriginY) and enumerate the windows that intersect the field. Keep all 64 arithmetic slots in boundary windows and substitute zero for invalid inputs, then bound stores independently. Removing padded keys would change the denominator and hence the model. The thread count in the figure is the ownership solution derived next, not a premise of the mathematical problem.

The source-level arithmetic size is also concrete: a dense C32 FFN performs 64·(32·128+128·32) scalar multiply-accumulate pairs; a wider FFN performs 64·[1·(32·128+128·32)+32²]. QKV and output projection add 64·4·32², and QKᵀ plus P×V add 1·2·64²·32. These are logical operation counts, not measured instruction throughput; publication and Half rounding remain visible in the source.

03. Warp and thread ownership

Replace scalar dot products with a warp-wide instruction only after choosing a useful tile. The available operation has M=16, N=8 and K=32. A 64-row window therefore divides into four M16 tiles, and a 32-channel head or branch result needs four N8 groups. A 4×4 spatial patch is a convenient 16-row ordering because it also keeps 2×2 transition cells local. It is a layout choice: the model’s natural row order must be permuted consistently in activations, bias and stores.

One warp can traverse all four M16 token tiles. Its four input tiles require 16 operand words per lane, and the four raw FFN output tiles require 32 accumulator words. Splitting these across four warps would shorten each token list, but attention would then need a cross-warp K/V exchange. Start with one warp and test the register budget before adding that exchange. This derives block=(32,1,1); it does not prove that count optimal on every GPU.

Now solve a single instruction’s lane map. Let g=lane//4 and q=lane%4. The accumulator owns rows g and g+8, and N8 group j owns channels 8j+2q and 8j+2q+1. Four neighboring lanes collectively cover one token’s C32 channels. Natural token 13, pixel(5,1), becomes tile 1,row 5,physical token21; g=5,q=2 gives lane 22 for channels 20/21. Lane22’s other row half is pixel(5,3), not another channel of the traced token.

One instruction computes a 16-token × 8-output-channel tile with a reduction of 32 channels. All 32 lanes participate in the same matrix operation. Each lane supplies four 32-bit A words, two 32-bit B words, and two 32-bit C words. Each C word contains two Half accumulators, so a lane owns four output elements. A source loop over output groups or reduction panels repeats this operation; it does not launch a new warp.

The exact instruction on this path is mma.sync.aligned.m16n8k32.row.col.f16.e4m3.e4m3.f16. Both the accumulator input and output are Half. Do not replace its numerical contract with FP32 accumulation when constructing an exact oracle. For the FP8 path, packing to E4M3 is a distinct rounding step; for the FP16 path a packed word simply holds two Half values.

Let lane L run from 0 to 31, g = L // 4 and q = L % 4. The matrix coordinates below describe instruction operands after any kernel-specific loads and shuffles. Storage layouts are designed to supply these coordinates cheaply.

A K32 A fragment supplies four words per lane; each N8 B fragment supplies two, and each N8 accumulator has two Half 2 words. Four N8 instructions produce C32; 1 K32 chunks reduce one C32 input panel. For a wider projection, repeat over 1 input panels while retaining the same accumulator. Build a one-hot matrix test before combining panels: an impulse in input channel 20 must multiply the model’s weight row 20 even when FP8 publication permutes its native K coordinate.

04. Resource budget

A fully retained hidden activation needs 64×128×1=8,192 published bytes. Stream one hidden C32 panel across the four token tiles instead: 64×32×1=2,048 bytes of logical operand extent, a fourfold reduction. The implementation can consume one token tile at a time within that panel. This does not make the kernel free of register pressure: the four input tiles, raw FFN residuals and later Q/K/V still have overlapping lifetimes. A shared spill candidate would trade that pressure for explicit loads and stores; compilation and measurement must decide whether that trade is useful.

05. Execution and scheduling

First implement a safe staged schedule: produce all X, finish the FFN, produce all Q/K/V, form scores, normalize, consume P×V, and project. Keep separate arrays until that version agrees with the oracle. Then remove only an intermediate whose last consumer is known. Stream hidden panel 0 through expansion, activation and contraction before panel 1; accumulation still visits hidden channels in order. This avoids a full 128-channel hidden lifetime, while retaining X and the final accumulator for their repeated uses.

The single warp can hand register fragments directly to the next stage. Start with one query tile, normalize all 64 keys, consume P×V, then release its scores. For FP8, a second candidate pairs two query tiles: 2×16=32 query rows allow one reciprocal owner per lane after transposing the row sums. A single 16-row tile has four lanes representing each row sum; paired ownership reduces duplicate inverse work but adds shuffles and simultaneous score state. Keep the ordered Half sums unchanged.

Place the only externally visible store after the final projection publication. Neither a score fragment nor a working-precision publication requires a global allocation merely because it is a named logical tensor.

Only now consider load scheduling. Reuse each loaded B panel across the owned token tiles, then release it before loading the next panel. This reduces repeated source loads but extends B’s live range. Adding cp.async, double buffering or more warps would require a new capacity and synchronization argument; none follows automatically from fusion. The flowchart expresses dependencies, not an SM issue timeline: different warps may reach a barrier at different times.

06. Trace one token through the source

Fix an interior, unshifted window at origin (0,0), with an 8×8 field for the byte examples. Follow natural token 13, pixel (5,1), through tile 1 and physical token 21. Its tile row is 5. For C32 panel zero, accumulator lane 22 owns channels 20/21 in r_Pair[2][0]. Other channels of this token are distributed across lanes 20–23; matrix products mix channels, and attention then mixes token values. Following a token means following this output row and its dependencies, not preserving one scalar unchanged.

Whenever this token is in the native published A layout, channel 20 is in word 2, low E4M3 byte; native K24 corresponds to model channel 20. For an ordinary packed allocation, its containing uint32 starts at tileBytes + 360 = 872 bytes. The allocation base is excluded. View inputs, low planes, feature planes and surfaces use their own equations below; this packed offset must not be applied to those storage layouts.

The transformer keeps this path in thread registers. It has no shared-memory swizzle. The feature-plane gather in an input frontend is a separate, real shared layout and is derived below.

Implement addresses before enabling any learned arithmetic

Build next. Construct a load→decode→identity→encode→store version first. Derive the native A address, the spatial-plane address and the packed B address independently; identical values do not imply interchangeable strides. Add the precision-specific weight record only after each address test passes.

For normal activation tiles use G + tileIndex·(512) + panel·(512) + chunk·512 + lane·16, with tileIndex=tileY·(Width/4)+tileX. The final term makes adjacent lanes load adjacent aligned 16-byte vectors. Tile 7, panel 0, chunk 0, lane 6 therefore begins at byte 3680 from G. A whole warp obtains 512 bytes for one K32 fragment panel. The packed producer layout removes the need to fetch a dense image and perform a separate runtime packing pass.

The spatial channel-plane map is different: G + (((plane·H+y)·W+x)·16) + 4(lane&3), where plane=panel·2+2·chunk+word/2, x=originX+((lane/4)&3), and y=originY+lane/16+2(word&1). Four lanes gather one 16-byte pixel vector, and the word's low bit changes the token row rather than the channel plane. Half-word or byte order remains the native fragment order inside that vector. This formula is needed to distinguish this packed-tile entry from a spatial view; this entry itself loads and stores tiles.

LoadWindowWeights reads the prepacked B operand. With output count N, reduction base r, output base o, chunk q and 16-output subpanel j, its byte offset is (r/32+q)·N·32 + (o/16+j)·512 + lane·16. Load weights once and reuse them across the owned token tiles; the cost is retaining B fragments in registers while A tiles are consumed.

126	FWindowValueTile<bFp8> r_Value[4];

134		#pragma unroll

139			if (ProjectionComponent < 2)

147				else

153				{

155					const uint32_t r_HighRows = TransposeM8n8(r_Projected.r_Pair[r_Column][1]);

159	}

162		LoadWindowWeights<bFp8>(g_PackedWeights + FConfig::ProjectionOffset, 0, 0, 32);

164	// FP8 follows the native two-query-tile softmax schedule. Keep the tested
165	// FP16 schedule independent until its register pressure is measured.
166	constexpr int CONST_QUERY_TILE_BATCH = bFp8 ? 2 : 1;
167	#pragma unroll
168	for (int r_FirstTile = 0; r_FirstTile < 4; r_FirstTile += CONST_QUERY_TILE_BATCH)
169	{
170		FWindowAccumulatorTile<64> r_Probabilities[CONST_QUERY_TILE_BATCH];
171		#pragma unroll
172		for (int r_LocalTile = 0; r_LocalTile < CONST_QUERY_TILE_BATCH; ++r_LocalTile)
173			r_Probabilities[r_LocalTile] = QueryKeyScores<bFp8>(
174				r_FirstTile + r_LocalTile, g_PackedWeights + FConfig::BiasOffset, r_Query, r_Key);
175		SoftmaxWindowPair(r_Probabilities);
176
177		#pragma unroll
178		for (int r_LocalTile = 0; r_LocalTile < CONST_QUERY_TILE_BATCH; ++r_LocalTile)
179		{
180			const int r_Tile = r_FirstTile + r_LocalTile;
181			const auto r_Attended = ProbabilityValues<bFp8>(r_Probabilities[r_LocalTile], r_Value);
182			#pragma unroll
183			for (int r_Column = 0; r_Column < 4; ++r_Column)
184				#pragma unroll
185				for (int r_RowHalf = 0; r_RowHalf < 2; ++r_RowHalf)
186					r_Ffn[r_Tile].r_Pair[r_Column][r_RowHalf] =
187						HalfMul(r_Ffn[r_Tile].r_Pair[r_Column][r_RowHalf], r_AttentionScale[r_Column]);
188			LinearWindow32(PublishWindow32<bFp8>(r_Attended), r_OutputWeights, r_Ffn[r_Tile]);
189
190			{
191				const int g_TileColumns = Parameters.Width / 4, g_TileRows = Parameters.Height / 4;
192				const int g_OriginTileX = (int(blockIdx.x) * 8 + Parameters.OriginX) / 4;
193				const int g_OriginTileY = (int(blockIdx.y) * 8 + Parameters.OriginY) / 4;
194				const int g_TileX = g_OriginTileX + (r_Tile & 1), g_TileY = g_OriginTileY + (r_Tile >> 1);
195				if (g_TileX >= 0 && g_TileX < g_TileColumns && g_TileY >= 0 && g_TileY < g_TileRows)
196				{
197					#pragma unroll
198					for (int r_Chunk = 0; r_Chunk < FConfig::InputChunks; ++r_Chunk)
199					{
200						const FWindowAFragment r_Output = PublishWindowChunk<bFp8>(r_Ffn[r_Tile], r_Chunk);
201						const uint64_t g_OutputAddress =
202							Parameters.g_Output +
203							uint64_t(g_TileY * g_TileColumns + g_TileX) * FConfig::TileBytes + r_Chunk * 512 +
204							int(threadIdx.x) * 16;
205						StoreNoAllocate(g_OutputAddress, make_uint4(r_Output.r_Word[0], r_Output.r_Word[1],
206																	r_Output.r_Word[2], r_Output.r_Word[3]));
207					}
208				}
209			}
210		}
211	}
212#else

214	__trap();
