Six sections, one forward design process

Read as the engineer who must build the operator. We know the mathematical contract first; the tile, ownership map and pipeline are choices we must justify. The lessons reconstruct a plausible design path to the checked implementation. They do not claim to reproduce its original authors' tuning history.

  1. The whole problem: define the model equation, shapes, layout and numerical boundaries. Write the simplest correct oracle. Identify repeated loads, intermediate writes or dependencies that make the baseline costly.
  2. One CTA: compare subdivisions of a concrete field. Calculate output work, reuse, reduction length, CTA count and tails. Choose a candidate and state what would make us revise it.
  3. Warp and thread: derive ownership from the instruction's operand contract. Map coordinates to lane words and addresses; establish coverage, exchange and synchronization requirements before coding the fast path.
  4. Resource budget: estimate accumulator state, operands, shared slots and barriers. Compare larger tiles or deeper buffers against lifetime and residency costs. Compiled allocation is still unknown at this point.
  5. Execution and scheduling: turn the dependency graph into prologue, steady state, drain and publication. Introduce overlap only after proving when a buffer becomes reusable. A logical schedule does not prescribe hardware warp issue order.
  6. One token: implement the design in successive milestones, carrying one numerical coordinate through storage and instructions. State each milestone's correctness test and performance hypothesis. Then compare the assembled candidate with recorded launch, allocation, SASS and NCU evidence. Revise predictions that fail.

The teaching progression takes inspiration from Emmanuel Alo's “Anatomy of a CUDA GEMM”: motivate successive mechanisms with a limitation of the simpler design. The operator equations, diagrams, layouts, hardware observations and measurements here come from this repository and its reports; the article's benchmark numbers and hardware generalizations are not used as evidence.

Keep an experiment ledger as you implement

Use the milestones below as a controlled development sequence. Some kernels need no shared memory or MMA; omit a mechanism when the operator offers no reuse or collective work to justify it. Alternatives in the lessons are design candidates, with no implied benchmark result.

MilestoneChangeAcceptance testEvidence available here
0 · define the oracleImplement the operator and its layout separately; preserve rounding and packing boundariesSmall hand-computable tensors, basis inputs, tails; exact bits for permutations, precision-appropriate comparison for arithmeticEquations, scalar pseudocode and worked coordinates; no newly benchmarked baseline GPU variant
1 · establish ownershipIntroduce the CTA/warp/lane decomposition without overlapEvery valid output has its specified owner; no illegal tail read or missing reduction rangeSource-derived maps and reproducible arithmetic checks; not a timing comparison
2 · replace the inner computationIntroduce packed operands and MMA, or the minimal word-copy/store pathCheck lane fragments against the oracle, inspect SASS, account for instruction countsExecuted instructions from the final binary; intermediate candidate timing remains open
3 · reduce traffic / overlapChange one reuse, fusion, staging or publication mechanismPreserve numerical boundaries and ownership; check races, allocation and shared service; time before and afterFinal resource/SASS/counter results only; they can falsify a prediction, not establish an A/B speedup
4 · integrate and challengeExercise admitted shapes, phases, boundaries and dependenciesCorrectness across fixtures, then end-to-end latency; retest optional branches separatelyOne selected logical call per entry on the stated fixture, including captured physical phases

Timing protocol for an open comparison: use the same GPU, binary flags, input tensors, precision boundaries and output contract; warm both variants; measure repeated batches with CUDA events outside Nsight Compute; alternate candidate order and report the median and spread. Check outputs before accepting any timing. Then profile both variants with identical collection settings and use source-correlated counters to explain the difference. Record changes in launch count and scratch traffic. An instrumented kernel duration or high tensor utilization is not an end-to-end speedup.

Arithmetic experiments executed when the guide is built

The machine-readable results record exhaustive spatial and packed-address round trips for both precisions at 4×4, 8×12 and 36×60; counter coverage at eight boundary counts and three block sizes; all 81 predicted static shared-memory sizes compared with recorded NCU; and all eight global linear kernels' four-warp output partitions and tensor-instruction counts. The packed-address decoder independently extracts the bit fields. These checks catch inconsistent diagrams, collision-prone addressing and incorrect budget/count arithmetic. They do not execute proposed CUDA variants, validate floating-point results, prove race freedom or measure a speedup. Regenerate with python tools/build_kernel_docs.py; the checks are in tools/kernel_docs/design_checks.py.

What was actually measured

Collected 13 October 2026 on NVIDIA RTX PRO 6000 Blackwell Workstation Edition, SM120, using Nsight Compute 2026.3.0 and CUDA 12.8.93. A fresh native SM120 library was built with -O3 -lineinfo. Every public entry has both a full report (including PM sampling) and a separate SourceCounters report. The full/source pair has a different replay pass set, so sample totals and instrumented timings need not agree between reports.

The trunk uses 3840×2160 requested image geometry, checkpoint weights, seeded random packed inputs scaled by .02, and five warmups. The model pads intermediate fields: level 0 is 1088×1920 and the C1024 bottleneck is 36×60 (2160 tokens). Only the first logical call of each public entry is selected by NVTX; dependencies still execute in schedule order. Any multi-launch split dispatch is retained in the raw report and per-entry JSON. Renderer entries are supplemental 2176×3840 fields, valid height 2160, with constant .25 current/color textures, no history/motion/depth/conditioning, point sampling, and seeded postprocess feature inputs. The supplemental C32 output-view uses 1088×1920 and phase 1. These fixtures exercise entries, not every optional branch or real-scene distribution.

Reproduce and inspect the evidence

Build receipt and source hashes · Exact collection commands · Evidence index. The library SHA-256 is recorded in every report receipt. The build regenerated a host policy header with whitespace-only formatting changes; token-equivalence was checked and the source checkout restored. CUDA kernel sources match the pinned revision. The harness and parser are checked into tools/profile_kernel_docs.py and tools/extract_kernel_doc_evidence.py.

ncu --nvtx --nvtx-include docs/ --set full --import-source yes \
  -o fp16-full python tools/profile_kernel_docs.py \
  --extension PATH_TO_NATIVE_SM120_LIBRARY --precision fp16 --output fp16-full.json
# Repeat with --section SourceCounters --section LaunchStats; then FP8.
python tools/extract_kernel_doc_evidence.py profile/YOUR_NEW_RUN

Use a new run directory containing harness/, reports/, analysis/ and REPORT.md. The installed NCU version has no source set, so the source collection requests its sections explicitly. Open .ncu-repz files in Nsight Compute to inspect full metrics, source and SASS. The extraction uses ncu_report, not rounded CLI tables.
