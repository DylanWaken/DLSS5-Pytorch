01. The whole problem

This kernel sits between the encoder C512→C1024 projection and the first global bottleneck block (records 30→31). The logical activation has shape [H,W,1024]. Local blocks group pixels into physical 4×4 tiles. Global attention needs the same pixels in row-major sequence order, where token t = yW+x. This entry converts the tiled representation into that sequence and initializes its padding.

No learned matrix, activation function, channel mixing, or floating-point arithmetic belongs here. A FP16 word is copied as 32 unchanged bits containing 2 adjacent Half channel values. Even NaN payloads and signed-zero bits survive the copy. The model-level equation is Y[y,x,c] = X[y,x,c]; the hard part is making that identity true for two different physical address functions. The architecture companion locates the boundary, but all layout definitions needed for this kernel are below.

Begin with the consumer contract: preserve every payload bit, and place it at the address the next operator expects. A scalar implementation could unpack channels, move them, and repack them. That adds conversions to a problem with no arithmetic. Instead, choose the largest already-defined indivisible payload in both layouts: one uint32 word. This changes the work unit without changing any value. The two integer layout functions below are the specification our implementation must satisfy.

Write a correctness baseline before parallelizing

Begin with a CPU loop over every logical token and every channel word. Give each input word a recognizable integer bit pattern. Implement the two address functions below, and copy between their results. Integer patterns are a better first test than random floating-point activations because a wrong pixel or channel remains easy to identify.

F is the packed-word address inside either representation; S changes a row-major pixel index into a spatial-tile index. Neither function changes the channel word. For this public entry, WPT=512 and the forward packing alignment is 16 tokens. These are compile-time precision choices, not runtime tensor metadata. The prepared deployment allocator can reserve a larger buffer than a single entry writes; distinguish allocation size from the kernel's actual loop extent.

02. One CTA: its concrete subproblem

Now divide the independent copies. At H=36, W=60, T=2160 we have 2160 × 512 = 1,105,920 logical word destinations. A thread can own one word because no destination depends on another. A CTA therefore needs neither a reduction tile nor a shared producer. We still need to choose how many such owners to group together.

Carry 256 threads forward as a candidate, not an analytically proven winner. It gives half a token per CTA; two CTAs per token. Block size changes scheduling granularity, not reuse or the address permutation. The current launcher uses this candidate; section 6 checks its actual launch.

Keep allocation and work bounds separate. The plan reserves 2176 tokens, but this direction covers 2160. Thus the last 32 CTAs should fail the loop bound. Derive this tail before writing a memory instruction; an allocation boundary is not a valid-data boundary.

03. Warp and thread ownership

Choose the logical index as the ownership rule before choosing its physical address. If lane ℓ owns i=256b+32w+ℓ, division by words-per-token yields one token and one channel word. This makes the uniqueness proof simple even though adjacent lanes do not necessarily touch adjacent physical words. A tempting 128-bit copy would group four words, but consecutive logical channel words have permuted physical offsets: cw=0,1,2,3 at token0 map to word offsets 0,4,8,12. One vector load cannot replace those four scalar loads. Derive a different ownership map and alignment proof before testing that candidate.

The prepared plan uses 256 threads per block. Flatten the launch as i=blockIdx.x×blockDim.x+threadIdx.x. Decompose the loop index as t=i//WPT and cw=i%WPT, then map to physical addresses. Notice that i is a logical work index, not the physical input or output offset. At the next iteration add gridDim.x×blockDim.x. This grid-stride loop preserves full coverage even when the launcher supplies fewer blocks than the number of words.

Each work index belongs to exactly one thread modulo the grid stride, and the address permutation is one-to-one. Consequently two threads never write the same output word. There is no cross-thread exchange, reduction, shared-memory tile, or barrier. Adjacent logical channel words are permuted within a compact 128-word panel, so the mapping retains spatial locality without a shared-memory transpose. The source uses ordinary 32-bit loads and stores; it does not explicitly vectorize them into 16-byte instructions or request asynchronous copies.

04. Resource budget

Budget the direct candidate before adding machinery. Its useful traffic is 4,423,680 input bytes + 4,423,680 output bytes = 8,847,360 bytes for this field. This is payload traffic; sectors, cache hits, replay and write policy determine the measured DRAM traffic. There are zero arithmetic FLOPs to amortize staging. A shared transpose would add at least one shared write and read per payload plus coordination. It is justified only if a demonstrated improvement in global transactions repays that cost.

Choose 0 application shared bytes, no barriers and no persistent fragment arrays for the first candidate. Keep one 32-bit payload live while calculating the two addresses. Pointer and multiply lowering can need several register words; counting C++ variables cannot predict the final allocation. Avoid a register cap until compilation gives a reason for one. L1/L2 residency remains hardware-managed. There is no shared-memory bank map or XOR swizzle in this candidate because it has no shared staging.

Budget checkpoint. Treat the bytes and live values above as a design estimate. Compile the candidate before accepting it: registers, local traffic, allocation rounding and residency can overturn this choice. We will compare the budget with the compiled allocation after constructing the implementation.

05. Execution and scheduling

Build the schedule from dependencies. The bounds check must precede a dereference; the input load must complete before its output store; the next work index follows the current copy. No edge crosses between threads. Therefore independent CTAs may run in any order and no block barrier is needed. Add a grid-stride loop so a smaller launch can still cover the same logical domain, then use stream ordering to release the output to the next kernel.

Do not add a copy/compute pipeline merely because other lessons use one: there is no matrix computation here to overlap with a staged tile. The experiments worth trying are alternative ownership/vector widths or CTA sizes. Hold the layout, bounds and copied bits fixed while timing them.

06. Trace one token through the source

Implement this candidate in three milestones. First implement and enumerate the pure address functions; then add the parallel integer copy; finally add the padded-tail rule and stream integration. Keep one test payload throughout: token 309, channel word 13, owned by thread 13, warp 0, lane 13 in CTA 618. A failure at the first milestone is an addressing bug; a failure after parallelization suggests coverage or a race; a tail-only failure identifies the extent rule. This separation makes each experiment diagnostic.

Derive the spatial token permutation

Take y=t//W and x=t%W. The tile coordinate is (y//4,x//4). There are W//4 tile columns; its linear tile index is (y//4)(W//4)+x//4. Multiply by 16 to skip complete tiles. The pixel within that tile is 4(y%4)+x%4. Therefore:

For width 60 and token 309, (y,x)=(5,9). The tile is (1,2), tile index 17, and the pixel inside it has index 5. Thus S(309)=17×16+5=277. This example separates pixel permutation from the more intricate word interleave; do not apply the 4×4 permutation independently to channels.

Derive the packed-word interleave

A naive t×WPT+cw address would not match the surrounding tensor-core kernels. Their fragments interleave 16 token rows with groups of eight channel words. Split the two indices into independent bit fields. The address below is in uint32 words; multiply it by four only when adding it to a byte pointer.

Handle the boundary exactly

The forward loop covers P×512 words, with P rounded up to 16. For t≥T it emits literal integer zero and does not evaluate an input read. Those bits represent positive zero in every packed channel. This is an actual initialization step used by downstream bottleneck kernels, not just an allocation convention.

The supported host contract supplies positive, aligned spatial geometry and separate input and output buffers. This permutation is not generally safe in-place: a thread can overwrite a word another thread has not read. Width must be compatible with the four-pixel tiling; the prepared model geometry satisfies that contract. Unsigned 32-bit loop arithmetic also means the launcher must keep products within its validated bounds.

Milestone 3: integrate the extent and tail contract

Implement the two pure integer functions first. Then add the launch index and grid stride. Finally add the direction-specific extent and tail rule. Keep the full 32-bit word as an integer throughout: unpacking/repacking would add work and could alter special values. The only precision-specific choices are words per token and the forward alignment.

Validate addresses before measuring bandwidth

  1. Enumerate every (token%16,cw%8) pair on CPU. Verify 128 unique offsets from 0 through 127. Then check the full geometry has no destination collisions.
  2. Fill packed words with an index-derived integer pattern. Compare this direction against the scalar baseline word for word; also run forward then inverse and compare every original bit.
  3. Use widths with more than one tile column and heights with more than one tile row. Include a token such as the worked example that moves between tile indices; a single 4×4 tile can hide permutation mistakes.
  4. Test a forward extent that requires padding where the geometry permits it, poison the destination first, and check only the specified aligned tail becomes zero. For inverse, poison padding in the input and put canaries after the spatial output.
  5. Repeat with an intentionally smaller grid to exercise a second grid-stride iteration. Test both precisions separately, because their word counts differ.

The optimization here is avoiding computation: copy packed bits, derive addresses with power-of-two divisions and remainders, and let independent threads stream through the permutation. The measured evidence below checks traffic and instructions for the documented workload; an optimization still needs a controlled before/after experiment.

Executed arithmetic experiment: the documentation build exhaustively checks the spatial permutation and independently decodes every packed address at 4×4, 8×12 and 36×60 for both word widths. All round trips pass. Inspect the cases and results. This validates the illustrated integer model; the proposed device bit-pattern, canary and reduced-grid tests above still need to be run on a new CUDA implementation.
