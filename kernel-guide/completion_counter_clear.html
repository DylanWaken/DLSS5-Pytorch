01. The model operation: initialize a dependency, not an activation

Split-reduction kernels in the C1024 bottleneck cooperate through scratch tensors and integer completion counters. Before a new invocation, the counters must say that no producer has finished. This kernel writes the sentinel -1 to each live counter. It does not transform a model tensor, but it prepares the scheduling state that makes the bottleneck's FFN, QKV and projection stages possible.

A counter is an int32 element in a device allocation. A later producer advances a counter according to its own split protocol; a consumer polls for the required progress. Resetting to zero would falsely indicate progress for protocols whose first published index is zero. The exact sentinel is therefore part of the algorithm, not an arbitrary memset value.

02. Start with the complete scalar algorithm

For i=0…CounterCount−1, assign counters[i]=-1. There is no reduction and no dependence among those assignments. A simple CUDA implementation gives one element to each thread. This is the final strategy too: a more elaborate staging scheme would add synchronization without removing any required store.

03. Derive ownership and addressing

The plan launches blocks of 256 threads and ceil(CounterCount/256) blocks. Thread threadIdx.x in block blockIdx.x owns i=256×blockIdx.x+threadIdx.x. The integer pointer conversion makes its byte address g_Counters+4i. Adjacent lanes therefore write adjacent four-byte counters. For 300 counters, block 0 writes indices 0…255 and block 1 lanes 0…43 write 256…299. Block 1 lane 44 owns 300 and returns before any access.

Unlike the repack kernels, this body has no grid-stride loop. The launcher must cover every live counter. A smaller grid would leave stale entries. A larger grid is safe within the validated index range because the upper-bound guard rejects excess threads. The CounterCount field counts elements, not bytes.

11	reinterpret_cast<int32_t*>(Parameters.g_Counters)[g_CounterIndex] = -1;
12}

04. Understand what makes the reset visible

Each counter has one writer during this launch, so atomic stores are unnecessary. A block barrier would coordinate only threads in one block and would not order a subsequent kernel. The host enqueues this reset before the corresponding work on the CUDA stream; that launch dependency is the relevant ordering boundary. Across streams, the caller must establish an equivalent event or other dependency. Clearing a counter while an earlier invocation still uses it is a race.

The store travels from a thread's immediate/register value through the normal global-memory path. Hardware caches may service that path; the source neither reserves a cache line nor synchronizes consumers by relying on cache residence. The producer/consumer kernel's own release, acquire, fence and polling instructions are a separate protocol. This initializer does not substitute for any of them.

05. Reconstruct and integrate the kernel

Use the exact ABI record in the appendix: a 64-bit device address, a 32-bit count, and reserved padding, totaling 16 bytes. Zero-initialize the record, bind a suitably aligned allocation large enough for 4×CounterCount bytes, select the covering grid, and enqueue before its users. Do not substitute an 8-bit count or write floating-point negative one. The desired 32-bit bit pattern is all ones.

06. Validate the sentinel and launch coverage

  1. Use counts 1, 255, 256, 257 and 300. Fill the allocation with a different pattern, launch a covering grid, and check every live value is signed -1.
  2. Put canaries after the live range. Verify the final partial block does not touch them.
  3. Repeat after a simulated completed invocation has left nonnegative values. A fresh reset must remove all stale progress.
  4. Check host launch ordering alongside the real consumer. A correct isolated reset cannot fix a cross-stream race or a consumer using the wrong counter array.

The kernel is intentionally small. Its useful optimizations are coalesced stores, no unnecessary reads, and one guard at the tail. Combining it with another launch is only valid if the full dependency protocol still guarantees that every counter is initialized before any consumer can poll it. No new launch-overhead measurement is claimed here.
