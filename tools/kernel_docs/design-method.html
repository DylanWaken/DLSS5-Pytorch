Six sections, one forward design process

Read as the engineer who must build the operator. We know the mathematical contract first; the tile, ownership map and pipeline are choices we must justify. The lessons reconstruct a plausible design path to the checked implementation. They do not claim to reproduce its original authors' tuning history.

  1. The whole problem: define the model equation, shapes, layout and numerical boundaries. Write the simplest correct oracle. Identify repeated loads, intermediate writes or dependencies that make the baseline costly.
  2. One CTA: compare subdivisions of a concrete field. Calculate output work, reuse, reduction length, CTA count and tails. Choose a candidate and state what would make us revise it.
  3. Warp and thread: derive ownership from the instruction's operand contract. Map coordinates to lane words and addresses; establish coverage, exchange and synchronization requirements before coding the fast path.
  4. Resource budget: estimate accumulator state, operands, shared slots and barriers. Compare larger tiles or deeper buffers against lifetime and residency costs. Compiled allocation is still unknown at this point.
  5. Execution and scheduling: turn the dependency graph into prologue, steady state, drain and publication. Introduce overlap only after proving when a buffer becomes reusable. A logical schedule does not prescribe hardware warp issue order.
  6. One token: implement the design in successive milestones, carrying one numerical coordinate through storage and instructions. State each milestone's correctness test and performance hypothesis. Then compare the assembled candidate with recorded launch, allocation, SASS and NCU evidence. Revise predictions that fail.

The teaching progression takes inspiration from Emmanuel Alo's “Anatomy of a CUDA GEMM”: motivate successive mechanisms with a limitation of the simpler design. The operator equations, diagrams, layouts, hardware observations and measurements here come from this repository and its reports; the article's benchmark numbers and hardware generalizations are not used as evidence.

Keep an experiment ledger as you implement

Use the milestones below as a controlled development sequence. Some kernels need no shared memory or MMA; omit a mechanism when the operator offers no reuse or collective work to justify it. Alternatives in the lessons are design candidates, with no implied benchmark result.

4 · integrate and challengeExercise admitted shapes, phases, boundaries and dependenciesCorrectness across fixtures, then end-to-end latency; retest optional branches separatelyOne selected logical call per entry on the stated fixture, including captured physical phases

Timing protocol for an open comparison: use the same GPU, binary flags, input tensors, precision boundaries and output contract; warm both variants; measure repeated batches with CUDA events outside Nsight Compute; alternate candidate order and report the median and spread. Check outputs before accepting any timing. Then profile both variants with identical collection settings and use source-correlated counters to explain the difference. Record changes in launch count and scratch traffic. An instrumented kernel duration or high tensor utilization is not an end-to-end speedup.

Arithmetic experiments executed when the guide is built

The machine-readable results record exhaustive spatial and packed-address round trips for both precisions at 4×4, 8×12 and 36×60; counter coverage at eight boundary counts and three block sizes; all 81 predicted static shared-memory sizes compared with recorded NCU; and all eight global linear kernels' four-warp output partitions and tensor-instruction counts. The packed-address decoder independently extracts the bit fields. These checks catch inconsistent diagrams, collision-prone addressing and incorrect budget/count arithmetic. They do not execute proposed CUDA variants, validate floating-point results, prove race freedom or measure a speedup.
