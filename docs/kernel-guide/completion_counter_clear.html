Completion-counter clear: initialize split progress

01. The whole problem

Split-reduction kernels in the C1024 bottleneck cooperate through scratch tensors and integer completion counters. Before a new invocation, the counters must say that no producer has finished. This kernel writes the sentinel -1 to each live counter. It does not transform a model tensor, but it prepares the scheduling state that makes the bottleneck's FFN, QKV and projection stages possible.

A counter is an int32 element in a device allocation. A later producer advances a counter according to its own split protocol; a consumer polls for the required progress. Resetting to zero would falsely indicate progress for protocols whose first published index is zero. The exact sentinel is therefore part of the algorithm, not an arbitrary memset value.

Start with the complete scalar algorithm

For i=0…CounterCount−1, assign counters[i]=-1. There is no reduction and no dependence among those assignments. A simple CUDA implementation gives one element to each thread. Keep this minimal candidate until a measured dependency-preserving alternative earns its extra complexity: staging would add synchronization without removing a required store.

02. One CTA: its concrete subproblem

The assignments are independent, so begin with one thread per int32 counter. The first 4K invocation needs N=136. A 128-thread candidate needs two CTAs; a 256-thread candidate needs one; a 512-thread candidate also needs one, with 376 rejected threads. For N=300 those choices need three, two and one CTA respectively. None changes the minimum 4N bytes stored. We cannot infer the fastest choice from the number of CTAs alone, especially for such a short launch.

Carry a 256-thread CTA forward: one block covers up to 1024 useful bytes and uses the same simple launch granularity as the word-copy kernels. Derive the grid as ceil(N/256). There is no grid-stride loop, so coverage is a launcher obligation. With N=136, threads 0…135 store and 136…255 return. Later deployment counts 272, 544 and 270 require different covering grids. We will validate the first 136-counter launch; use the illustrative N=300 trace to force a partial second block during design testing.

03. Warp and thread ownership

Choose consecutive counters for consecutive lanes. Lane ℓ in warp w of block b owns i=256b+32w+ℓ and byte address base+4i. This creates one writer per valid element and contiguous per-warp addresses. No input needs to be shared, so shuffles, shared exchange and atomics have no role in the candidate. Prove uniqueness and coverage before worrying about store throughput.

The plan launches blocks of 256 threads and ceil(CounterCount/256) blocks. Thread threadIdx.x in block blockIdx.x owns i=256×blockIdx.x+threadIdx.x. The integer pointer conversion makes its byte address g_Counters+4i. Adjacent lanes therefore write adjacent four-byte counters. For 300 counters, block 0 writes indices 0…255 and block 1 threads 0…43 write 256…299. Block 1 thread 44 owns 300 and returns before any access.

Unlike the repack kernels, this body has no grid-stride loop. The launcher must cover every live counter. A smaller grid would leave stale entries. A larger grid is safe within the validated index range because the upper-bound guard rejects excess threads. The CounterCount field counts elements, not bytes.

Convert the flat thread index into warp and lane explicitly: thread 43 is warp 1, lane 11; thread 44 is warp 1, lane 12. A hardware warp has only 32 lanes. In the measured N=136 case, four warps are fully active, warp 4 has eight valid lanes, and warps 5–7 perform no stores.

04. Resource budget

The lower bound is 4N useful bytes written and no input reads: 544 bytes for N=136, or 1200 for the teaching N=300 case. Start with 0 application shared bytes and no persistent arrays. The live state consists of a pointer/index, a predicate and the −1 operand, whose exact register cost is compiler-dependent. There is no arithmetic intensity or reuse benefit to trading extra shared storage for fewer global operations.

A high occupancy target would be misleading here: a single CTA cannot fill a 188-SM device. Enlarging the block does not create more useful work. The first performance hypothesis should be that launch/dependency overhead matters; test that with end-to-end timing, since NCU kernel duration alone does not measure host launch overhead. Preserve the simplest store-only candidate until an experiment justifies fusion or a different launch shape.

Budget checkpoint. Treat the bytes and live values above as a design estimate. Compile the candidate before accepting it: registers, local traffic, allocation rounding and residency can overturn this choice. We will compare the budget with the compiled allocation after constructing the implementation.

05. Execution and scheduling

Design ordering from the consumer backward. A split consumer must never mistake stale progress for current progress. Therefore the entire clear must happen after prior users finish and before new producers or polling consumers begin. Put that dependency in the stream schedule. A barrier inside the clear could not establish this ordering across launches, and a global atomic would not repair a missing launch dependency.

Each counter has one writer during this launch, so atomic stores are unnecessary. A block barrier would coordinate only threads in one block and would not order a subsequent kernel. The host enqueues this reset before the corresponding work on the CUDA stream; that launch dependency is the relevant ordering boundary. Across streams, the caller must establish an equivalent event or other dependency. Clearing a counter while an earlier invocation still uses it is a race.

The store travels from a thread's immediate/register value through the normal global-memory path. Hardware caches may service that path; the source neither reserves a cache line nor synchronizes consumers by relying on cache residence. The producer/consumer kernel's own release, acquire, fence and polling instructions are a separate protocol. This initializer does not substitute for any of them.

06. Trace one token through the source

Build three small milestones: an isolated sentinel store, the guarded parallel launch, and integration before a real split producer. Check exact bits after the first; test counts around 256 and canaries after the second; repeat invocations with stale nonnegative counters after the third. This kernel moves a control word, not an activation token. Our N=300 boundary experiment follows CTA 1, thread 43 (warp 1, lane 11): i=299 passes the guard and stores FF FF FF FF at base+1196. Thread 44 computes 300 and must exit. These checks isolate sentinel, coverage and ordering errors before profiling.

Implement the guarded store, then inspect its lowering

Express the index using blockDim.x so the covering-grid experiment can change block size without changing the address rule. Reject the tail before dereferencing the int32 pointer; the launcher must validate the signed index domain. Emit one ordinary assignment of −1. Our prediction is a store path with no input payload load or collective. Now compare that prediction with the complete implementation and the measured instruction evidence at the end of this section.

Integrate the candidate with its ABI and consumers

Use the exact ABI record in the appendix: a 64-bit device address, a 32-bit count, and reserved padding, totaling 16 bytes. Zero-initialize the record, bind a suitably aligned allocation large enough for 4×CounterCount bytes, select the covering grid, and enqueue before its users. Do not substitute an 8-bit count or write floating-point negative one. The desired 32-bit bit pattern is all ones.

Validate the sentinel and launch coverage

  1. Use counts 1, 255, 256, 257 and 300. Fill the allocation with a different pattern, launch a covering grid, and check every live value is signed -1.
  2. Put canaries after the live range. Verify the final partial block does not touch them.
  3. Repeat after a simulated completed invocation has left nonnegative values. A fresh reset must remove all stale progress.
  4. Check host launch ordering alongside the real consumer. A correct isolated reset cannot fix a cross-stream race or a consumer using the wrong counter array.

The kernel is intentionally small. Its useful optimizations are coalesced stores, no unnecessary reads, and one guard at the tail. Combining it with another launch is only valid if the full dependency protocol still guarantees that every counter is initialized before any consumer can poll it. The NCU duration below is one instrumented launch, not an end-to-end estimate of host launch overhead.

Executed arithmetic experiment: enumerate the proposed writer map at counts 1, 136, 255, 256, 257, 272, 300 and 544 with 128, 256 and 512 threads per CTA. Every covering grid gives exactly one writer per live word and rejects every tail index. All 24 cases pass. This checks launch arithmetic on the CPU; the device sentinel and stream-dependency experiments above remain separate correctness obligations.
