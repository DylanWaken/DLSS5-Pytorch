01. The whole problem

Target entry: window_block_c256_output_view_fp16. This entry implements the ordinary C256 block used in records 15–22 and 48–55, but publishes into spatial channel planes. The result still has logical shape [H,W,256]. Its output layout is designed for a consumer that addresses individual spatial positions. The FFN is 8 complete-input branches, each 256 → 128 → 32, followed by a 256 → 256 mixing matrix. The attention has 8 heads, each with 32 channels. There is no pre-FFN LayerNorm and no sparse routing decision. Every FFN works independently at each token; the attention is where 64 positions exchange information. The architecture document is useful context, but all mechanics needed for this entry are developed below.

Write the ordinary block as Zraw=FFN(X)+sffn⊙R; Z=Publish(Zraw); Q,K,V=project(Z); A=Publish(normalize_keys(E(QKᵀ+bias))V); Yraw=project(A)+sattn⊙Z. This entry publishes working operands as Half, while the matrix accumulators, residual products, activation and reductions use packed Half arithmetic. “Raw” identifies a value before the next publication, not an FP32 promise. The model equation alone leaves reduction order and physical placement unspecified; those are the kernel-design problem.

A correctness oracle for the complete operator

Start with the following nested-loop interpretation. A token index denotes a spatial position, a channel index selects its feature, and a head index selects one 32-channel attention space. The oracle is deliberately expensive: it can materialize every hidden tensor and the 64 × 64 score matrix. It establishes which values may communicate and where publication belongs. To validate the final bit pattern, replace its abstract dot products and sums with the exact Half instruction/reduction order introduced below; a generic FP32 PyTorch implementation is only a mathematical and shape check.

A fully staged implementation would write the hidden FFN tensor, branch concatenation, QKV, scores, probabilities and attended values to global memory, then read them back in separate launches. For one head, a score tensor alone is 4096 Half values, or 8192 bytes; a separate write and read would transfer 16384 logical bytes before considering cache effects. The implementation removes these particular intermediate transfers by choosing an ownership map that keeps their producers and consumers together. The tradeoff is longer register lifetimes, and for multiple warps, explicit shared-memory synchronization.

Find the first avoidable cost

A correct first version runs the ordinary block into a temporary published [64,256] tensor, then scatters it into spatial planes. The temporary write plus read costs 2×64×256×2=65,536 logical bytes per window. Direct final addressing may remove it, provided each valid view location is written once and invalid locations remain untouched.

The following design is a reconstruction from the model and current source. The staged baseline and alternative partitions are teaching candidates, not claims about the author’s historical experiments or measured faster/slower variants. Byte counts are logical traffic excluding weights, cache reuse and transaction overhead.

02. One CTA: its concrete subproblem

Start by assigning one output token to a thread. That is correct, but its query must read all 64 keys and values. Grouping 16 query rows in a CTA improves reuse, yet four such CTAs still need the same K/V neighborhood. One head’s K plus V is 2×64×32×2=8,192 working bytes; four independently loaded query groups request 32,768 logical bytes instead of 8,192, before cache effects. A CTA per head avoids that duplication, but the final 256→256 projection must combine all heads and would need another exchange or launch. These dependencies motivate trying one CTA per complete window.

The selected subproblem therefore includes 64 FFNs, 8 Q/K/V projections, every 64×64 head interaction and the final cross-head projection. Its scope is an algebraic consequence of local attention; the choice to fit it into one CTA is an implementation decision. The view adapter, when present, changes where this domain is loaded or stored rather than which tokens attend each other.

Make that choice concrete on a 16×16 field: a 2×2 CTA grid covers four unshifted windows; CTA(1,0) starts at (8,0). With a phase offset, use (8·blockIdx.x+OriginX,8·blockIdx.y+OriginY) and enumerate the windows that intersect the field. Keep all 64 arithmetic slots in boundary windows and substitute zero for invalid inputs, then bound stores independently. Removing padded keys would change the denominator and hence the model. The thread count in the figure is the ownership solution derived next, not a premise of the mathematical problem.

The source-level arithmetic size is also concrete: a dense C32 FFN performs 64·(32·128+128·32) scalar multiply-accumulate pairs; a wider FFN performs 64·[8·(256·128+128·32)+256²]. QKV and output projection add 64·4·256², and QKᵀ plus P×V add 8·2·64²·32. These are logical operation counts, not measured instruction throughput; publication and Half rounding remain visible in the source.

03. Warp and thread ownership

Replace scalar dot products with a warp-wide instruction only after choosing a useful tile. The available operation has M=16, N=8 and K=16. A 64-row window therefore divides into four M16 tiles, and a 32-channel head or branch result needs four N8 groups. A 4×4 spatial patch is a convenient 16-row ordering because it also keeps 2×2 transition cells local. It is a layout choice: the model’s natural row order must be permuted consistently in activations, bias and stores.

A two-token token-parallel warp at C256 would retain 2×8×8=128 input words and 2×8×8=128 output accumulator words, before expansion weights or hidden accumulators. Distribute the eight full-input branches instead: each warp produces one C32 branch panel for all four token tiles, only 32 output words per lane. All eight still read all 256 input channels, so this is a storage/work partition rather than sparse routing. Shared exchange and barriers are the cost of that reduced per-warp result extent. This derives block=(32,8,1); it does not prove that count optimal on every GPU.

Now solve a single instruction’s lane map. Let g=lane//4 and q=lane%4. The accumulator owns rows g and g+8, and N8 group j owns channels 8j+2q and 8j+2q+1. Four neighboring lanes collectively cover one token’s C32 channels. Natural token 13, pixel(5,1), becomes tile 1,row 5,physical token21; g=5,q=2 gives lane 22 for channels 20/21. Lane22’s other row half is pixel(5,3), not another channel of the traced token.

One instruction computes a 16-token × 8-output-channel tile with a reduction of 16 channels. All 32 lanes participate in the same matrix operation. Each lane supplies four 32-bit A words, two 32-bit B words, and two 32-bit C words. Each C word contains two Half accumulators, so a lane owns four output elements. A source loop over output groups or reduction panels repeats this operation; it does not launch a new warp.

The exact instruction on this path is mma.sync.aligned.m16n8k16.row.col.f16.f16.f16.f16. Both the accumulator input and output are Half. Do not replace its numerical contract with FP32 accumulation when constructing an exact oracle. For the FP8 path, packing to E4M3 is a distinct rounding step; for the FP16 path a packed word simply holds two Half values.

Let lane L run from 0 to 31, g = L // 4 and q = L % 4. The matrix coordinates below describe instruction operands after any kernel-specific loads and shuffles. Storage layouts are designed to supply these coordinates cheaply.

A K16 A fragment supplies four words per lane; each N8 B fragment supplies two, and each N8 accumulator has two Half 2 words. Four N8 instructions produce C32; 2 K16 chunks reduce one C32 input panel. For a wider projection, repeat over 8 input panels while retaining the same accumulator. Build a one-hot matrix test before combining panels: an impulse in input channel 20 must multiply the model’s weight row 20 even when FP8 publication permutes its native K coordinate.

04. Resource budget

All 8 branches read X, then all output panels read branch results. Keeping separate shared X, branch, Z and attended arrays would cost 131,072 bytes; their sequential lifetimes permit one 32,768-byte slab if reader completion is enforced. A two-stage copy ring would double the slab to 65,536 bytes before any barrier metadata. It is a different candidate, not a free improvement. For attention, two retained attended C32 tiles cost 2×8=16 accumulator words per lane; four cost 32. C256 uses the four-tile candidate in the construction below. Larger batches reduce exchange rounds but lengthen live ranges; the budget alone cannot select the faster batch.

05. Execution and scheduling

First implement a safe staged schedule: produce all X, finish the FFN, produce all Q/K/V, form scores, normalize, consume P×V, and project. Keep separate arrays until that version agrees with the oracle. Then remove only an intermediate whose last consumer is known. Stream hidden panel 0 through expansion, activation and contraction before panel 1; accumulation still visits hidden channels in order. This avoids a full 128-channel hidden lifetime, while retaining X and the final accumulator for their repeated uses.

Begin with separate shared arrays. To collapse them into one slab, insert a reader-completion barrier before overwrite and a writer-completion barrier before consuming the replacement. The wide FFN requires these boundaries at X→branches and branches→Z; saving the scaled residual before overwrite is part of the correctness dependency. An attention batch of 4 query tiles keeps 32 attended accumulator words per lane before head exchange. Compare that with 16 words for the other batch size before choosing an experiment.

For the spatial input variant, move the gather into the first operand load; for spatial output, move scattering into the last store. In either case the word predicates replace a conversion pass and must preserve the same decoded tensor.

Only now consider load scheduling. Reuse each loaded B panel across the owned token tiles, then release it before loading the next panel. This reduces repeated source loads but extends B’s live range. Adding cp.async, double buffering or more warps would require a new capacity and synchronization argument; none follows automatically from fusion. The flowchart expresses dependencies, not an SM issue timeline: different warps may reach a barrier at different times.

06. Trace one token through the source

Fix an interior, unshifted window at origin (0,0), with an 8×8 field for the byte examples. Follow natural token 13, pixel (5,1), through tile 1 and physical token 21. Its tile row is 5. For C32 panel zero, accumulator lane 22 owns channels 20/21 in r_Pair[2][0]. Other channels of this token are distributed across lanes 20–23; matrix products mix channels, and attention then mixes token values. Following a token means following this output row and its dependencies, not preserving one scalar unchanged.

Whenever this token is in the native published A layout, channel 20 is in chunk 1, word 0, low Half; native K4 + chunk base16 = channel 20. For an ordinary packed allocation, its containing uint32 starts at tileBytes + 864 = 9056 bytes. The allocation base is excluded. View inputs, low planes, feature planes and surfaces use their own equations below; this packed offset must not be applied to those storage layouts.

The same local tile/panel/chunk/lane map addresses the shared exchange slab: ((((tile×8+panel)×2+chunk)×32+lane)×16)+4·word. Our selected word again begins at shared byte 9056; its 32-bit bank index is (9056//4) mod32 = 24. There is no XOR swizzle in this slab. A full uint4 accesses four successive bank words; a bank-index diagram alone cannot establish a bank conflict without the instruction transaction grouping and measured wavefront counts.

Implement addresses before enabling any learned arithmetic

Build next. Construct a load→decode→identity→encode→store version first. Derive the native A address, the spatial-plane address and the packed B address independently; identical values do not imply interchangeable strides. Add the precision-specific weight record only after each address test passes.

For normal activation tiles use G + tileIndex·(8192) + panel·(1024) + chunk·512 + lane·16, with tileIndex=tileY·(Width/4)+tileX. The final term makes adjacent lanes load adjacent aligned 16-byte vectors. Tile 7, panel 1, chunk 1, lane 6 therefore begins at byte 58976 from G. A whole warp obtains 512 bytes for one K16 fragment panel. The packed producer layout removes the need to fetch a dense image and perform a separate runtime packing pass.

The spatial channel-plane map is different: G + (((plane·H+y)·W+x)·16) + 4(lane&3), where plane=panel·4+2·chunk+word/2, x=originX+((lane/4)&3), and y=originY+lane/16+2(word&1). Four lanes gather one 16-byte pixel vector, and the word's low bit changes the token row rather than the channel plane. Half-word or byte order remains the native fragment order inside that vector. This formula is needed on the output path.

LoadWindowWeights reads the prepacked B operand. With output count N, reduction base r, output base o, chunk q and 16-output subpanel j, its byte offset is (r/16+q)·N·32 + (o/16+j)·512 + lane·16. Each K16 panel occupies 32 bytes per output column in this precision. For N=128,r=32,o=16,j=0,q=0,lane=6 the offset is 8800. This is a packed matrix address, not (r·N+o)·sizeof(element). Lay out the complete packed weight record

Let C=256, H=C/32=8, and b=2 bytes per matrix operand. Put H expansion matrices first, each C×128×b bytes, followed by H contraction matrices, each 128×32×b bytes. Thus ContractOffset=H·C·128·b=524288, and MixOffset=ContractOffset+H·128·32·b=589824. The C×C mixing matrix follows. For the ordinary profile, 16 padding bytes precede the C Half FFN scales, and another 16 precede QKV. QKV occupies 3·C²·b bytes; the H Half attention-bias tables occupy H·8192 bytes. The H FP32 head scales are rounded up to a 16-byte allocation before the C×C projection. Finally come C Half attention-residual scales. These sizes derive every later pointer from the record base instead of relying on unexplained offsets.
